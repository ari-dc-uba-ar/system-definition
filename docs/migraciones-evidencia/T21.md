## Primer rojo propuesto — cobertura destructiva discard de campo completo

Archivo nuevo: `consumers/postgres-migrations/test/destructive-decision-test.ts`.

Este rojo fija sólo la primera frontera T21, reutilizando `inferStructureChanges` T18 y `compileDraft` T18. No autoriza SQL manual, resolución `migrate`, particiones, CLI de resolución ni grafo completo.

El test exige:

1. al retirar una tabla, el cambio destructivo de tabla enumera determinísticamente todas sus columnas persistidas en `affectedFields`;
2. que `inspectDraft` ya muestre el DROP no basta: si falta la decisión destructiva, `compileDraft` devuelve `migration.authoringPending` antes de aceptar el borrador;
3. un único `discard` de campo completo (`partitionCheck=null`) con razón no vacía permite compilar cuando los efectos ya fueron inspeccionados y la decisión exacta queda transportada a `CompiledAuthoringInfo.decisions`;
4. un `changeId` obsoleto/ajeno al diff histórico reconstruido devuelve `migration.invalidReference`;
5. dos decisiones para la misma fuente/cambio o un `discard.reason` vacío devuelven `migration.authoringInvalid`, sin convertir una aprobación puntual en cobertura más amplia.

La resolución `migrate` permanece representada por el contrato especificado, pero su prueba de bindings/outputs/conservación se deja para el siguiente slice T21 junto con particiones. SQL manual queda todavía más adelante.

### Rojo esperado contra producción actual

La producción actual mantiene `MigrationDraftInfo.decisions` y `CompiledAuthoringInfo.decisions` como `unknown[]` y no exporta `DestructiveDecisionInfo`. Por eso el primer límite esperado al ejecutar el test es TypeScript:

```text
test/destructive-decision-test.ts: error TS2305:
Module '../src/authoring' has no exported member 'DestructiveDecisionInfo'.
```

Una vez agregado el tipo documentado, los asserts runtime fuerzan la validación histórica de cobertura: hoy `compileDraft` acepta un DROP ya inspeccionado sin decisiones y, en sentido contrario, rechaza cualquier `decisions.length > 0` con el pending genérico T18.

Validación local del rojo en el árbol extraído: el `tsconfig` consumidor completo no puede ser autoritativo porque el ZIP no trae `@types/node`/`@types/mocha`. Con shims exclusivamente ambientales para esos tipos, un compile enfocado del test produjo exactamente el límite esperado y ningún otro diagnóstico de producto:

```text
consumers/postgres-migrations/test/destructive-decision-test.ts(7,10): error TS2305:
Module '"../src/authoring"' has no exported member 'DestructiveDecisionInfo'.
exit=2
```

La corrida Docker del desarrollador sigue siendo el oráculo para observar el rojo en el entorno real.

## Segundo rojo propuesto — migrate, particiones y preservación antes de DROP

Archivo nuevo: `consumers/postgres-migrations/test/destructive-migrate-partition-test.ts`.

Este rojo abre sólo la segunda frontera T21 y reutiliza los contratos T19/T20 ya completados. No autoriza SQL manual, CASCADE, el manifest persistido completo ni la integración de gates T22.

El test exige:

1. una resolución `migrate` sólo compila cuando `dataMigrationId` existe, la migración consume exactamente la fuente destructiva y cada nombre de `outputs` está ligado a una escritura de esa migración;
2. migration inexistente, `outputs=[]`, fuente no consumida u output no escrito se rechazan como referencia/autoría inválida en vez de convertir la selección en aprobación amplia;
3. una misma fuente puede dividirse en decisiones por partición sólo mediante `partitionCheck` explícitos y distintos, conservando las decisiones exactas en el resultado compilado;
4. checks de partición duplicados, mezclar una decisión de campo completo con decisiones particionadas o usar un recurso que no sea `kind=check` se rechazan;
5. el grafo compilado contiene la operación de preservación y la eliminación destructiva, y el orden topológico coloca la data migration —incluidos sus checks T20— antes del DROP de la fuente.

La prueba no fija IDs sintéticos de operaciones ni SQL concreto: comprueba sólo la pertenencia por `dataMigrationIds`/`changeIds` y el orden relativo observable. Así deja al implementador reutilizar el compilador T20 sin inventar un segundo motor.

### Rojo observado contra el slice #1

El nuevo test compila contra el contrato actual. En una ejecución local enfocada con `--skipLibCheck` únicamente para aislar declaraciones ambientales del ZIP, los cinco casos fallan en la frontera esperada:

```text
T21 migrate decisions, partitions and preservation order
  0 passing; 5 failing
```

Los casos válidos reciben todavía `migration.authoringPending`; los negativos que esperan `migration.invalidReference`/`migration.authoringInvalid` reciben el mismo pending genérico. Es el comportamiento deliberado del slice #1, que difiere `draft.data`, `migrate` y particiones.

La corrida Docker del desarrollador sigue siendo el oráculo para observar este rojo en el entorno real antes de implementar.

## Límite de autorización del segundo rojo

No se modifica producción con este patch. Si el desarrollador responde explícitamente `T21 second red approved`, queda autorizado únicamente:

- integrar en `compileDraft` las `DataMigrationInfo` ya completadas necesarias para decisiones `migrate`;
- validar `dataMigrationId`, consumo de `source`, `outputs` escritos y referencias de partición;
- permitir múltiples decisiones de una fuente sólo cuando estén separadas por `partitionCheck` válidos, sin mezclar cobertura de campo completo;
- construir/ordenar el mínimo grafo de operaciones para que la preservación T20 y sus checks precedan a la eliminación destructiva correspondiente.

Siguen fuera de autorización: SQL manual/add-sql, análisis/bloqueo CASCADE, conflictos de escritores generales, manifest persistido/hashes/gates T22 y cualquier ampliación de CLI.
