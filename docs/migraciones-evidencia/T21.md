## Primer rojo propuesto — cobertura destructiva discard de campo completo

Archivo nuevo: `consumers/postgres-migrations/test/destructive-decision-test.ts`.

Este rojo fija sólo la primera frontera T21, reutilizando `inferStructureChanges` T18 y `compileDraft` T18. No autoriza SQL manual, resolución `migrate`, particiones, CLI de resolución ni grafo completo.

El test exige:

1. al retirar una tabla, el cambio destructivo de tabla enumera determinísticamente todas sus columnas persistidas en `affectedFields`;
2. que `inspectDraft` ya muestre el DROP no basta: si falta la decisión destructiva, `compileDraft` devuelve `migration.authoringPending` antes de aceptar el borrador;
3. un único `discard` de campo completo (`partitionCheck=null`) con razón no vacía permite compilar cuando los efectos ya fueron inspeccionados y la decisión exacta queda transportada a `CompiledAuthoringInfo.decisions`;
4. un `changeId` obsoleto/ajeno al diff histórico reconstruido devuelve `migration.invalidReference`;
5. dos decisiones para la misma fuente/cambio o un `discard.reason` vacío devuelven `migration.authoringInvalid`, sin convertir una aprobación puntual en cobertura más amplia.

La resolución `migrate` permanece representada por el contrato especificado, pero su prueba de bindings/outputs/conservación se deja para el siguiente slice T21 junto con particiones. SQL manual queda todavía más adelante.

### Rojo esperado contra producción actual

La producción actual mantiene `MigrationDraftInfo.decisions` y `CompiledAuthoringInfo.decisions` como `unknown[]` y no exporta `DestructiveDecisionInfo`. Por eso el primer límite esperado al ejecutar el test es TypeScript:

```text
test/destructive-decision-test.ts: error TS2305:
Module '../src/authoring' has no exported member 'DestructiveDecisionInfo'.
```

Una vez agregado el tipo documentado, los asserts runtime fuerzan la validación histórica de cobertura: hoy `compileDraft` acepta un DROP ya inspeccionado sin decisiones y, en sentido contrario, rechaza cualquier `decisions.length > 0` con el pending genérico T18.

Validación local del rojo en el árbol extraído: el `tsconfig` consumidor completo no puede ser autoritativo porque el ZIP no trae `@types/node`/`@types/mocha`. Con shims exclusivamente ambientales para esos tipos, un compile enfocado del test produjo exactamente el límite esperado y ningún otro diagnóstico de producto:

```text
consumers/postgres-migrations/test/destructive-decision-test.ts(7,10): error TS2305:
Module '"../src/authoring"' has no exported member 'DestructiveDecisionInfo'.
exit=2
```

La corrida Docker del desarrollador sigue siendo el oráculo para observar el rojo en el entorno real.

## Segundo rojo propuesto — migrate, particiones y preservación antes de DROP

Archivo nuevo: `consumers/postgres-migrations/test/destructive-migrate-partition-test.ts`.

Este rojo abre sólo la segunda frontera T21 y reutiliza los contratos T19/T20 ya completados. No autoriza SQL manual, CASCADE, el manifest persistido completo ni la integración de gates T22.

El test exige:

1. una resolución `migrate` sólo compila cuando `dataMigrationId` existe, la migración consume exactamente la fuente destructiva y cada nombre de `outputs` está ligado a una escritura de esa migración;
2. migration inexistente, `outputs=[]`, fuente no consumida u output no escrito se rechazan como referencia/autoría inválida en vez de convertir la selección en aprobación amplia;
3. una misma fuente puede dividirse en decisiones por partición sólo mediante `partitionCheck` explícitos y distintos, conservando las decisiones exactas en el resultado compilado;
4. checks de partición duplicados, mezclar una decisión de campo completo con decisiones particionadas o usar un recurso que no sea `kind=check` se rechazan;
5. el grafo compilado contiene la operación de preservación y la eliminación destructiva, y el orden topológico coloca la data migration —incluidos sus checks T20— antes del DROP de la fuente.

La prueba no fija IDs sintéticos de operaciones ni SQL concreto: comprueba sólo la pertenencia por `dataMigrationIds`/`changeIds` y el orden relativo observable. Así deja al implementador reutilizar el compilador T20 sin inventar un segundo motor.

## Tercer rojo propuesto — SQL manual, residual y límite CASCADE

Archivo nuevo: `consumers/postgres-migrations/test/manual-sql-residual-test.ts`.

Este rojo abre sólo la tercera frontera T21. Reutiliza el diff/replay T18, las decisiones destructivas de slices #1/#2 y el parser/runner SQL existente. No autoriza todavía el manifest persistido completo, hashes/gates de publicación/deployment, CLI `add-sql`/resolver completo ni T22.

El test exige:

1. un paso manual con contrato explícito puede implementar una parte del diff; `compileDraft` materializa ese paso en `MigrationInfo.steps`, liga su operación a los `changeId` reclamados y, después de inspeccionar los efectos, genera **sólo** los cambios preservadores todavía residuales, sin duplicar lo que el manual ya realizó;
2. `implementsChanges` obsoleto, el mismo cambio reclamado por más de un paso o un `run` que no sea recurso `kind=sql` se rechazan de forma determinística (`invalidReference`/`authoringInvalid`/`invalidResourceKind`);
3. si un cambio reclamado por SQL manual reaparece después del replay/inspección, o el contrato declara destruir un objeto que el SSOT deseado conserva, se rechaza como autoría inválida en vez de ocultarlo regenerando el cambio;
4. un DROP manual exige exactamente la misma decisión destructiva explícita que un DROP generado; con la decisión válida el paso manual queda en el plan, sin crear un bypass de cobertura;
5. SQL manual destructivo que usa `CASCADE` se rechaza como `migration.unsupportedSql`; las dependencias deben representarse/ordenarse explícitamente.

El fixture de runtime del test expone además `readSql(ref)` para entregar los bytes exactos del recurso manual. La producción actual todavía no consume ese puerto porque bloquea cualquier `draft.manual.length > 0` antes de reconstrucción/replay; el slice autorizado podrá tipar ese puerto de forma compatible con los runtimes sin SQL manual (por ejemplo, opcional y obligatorio sólo cuando exista un paso manual).

### Rojo observado contra los slices #1+#2 verdes

```text
  0 passing; 5 failing
```

Los cinco fallos provienen de la frontera deliberada actual: `compileDraft` sigue devolviendo `migration.authoringPending` con razón `manual SQL requires a later T21 slice`, mientras el rojo exige la semántica manual/residual/CASCADE documentada.

## Cuarto rojo propuesto — manifest local, grafo manual y sesión add-sql

Archivo nuevo: `consumers/postgres-migrations/test/authoring-final-integration-test.ts`.

Este es el último rojo previsto dentro de T21. Completa únicamente la integración local de autoría que todavía está deliberadamente bloqueada por el slice #3. No autoriza persistir el manifest dentro del artifact publicado, modificar `migrationHash`, loader/buildMigrationPlan, verification evidence, gates, CI ni trabajo T22/T23.

El test exige:

1. checks `before`/`after` de un paso manual se conservan en el manifest compilado: un `before` previo al primer step queda en `migration.before` y el `after` queda como checkpoint del step, sin perder el contrato del paso;
2. `dependsOn` manual produce orden topológico aunque el draft declare los pasos al revés; las operaciones compiladas observan el mismo orden;
3. dependencia inexistente se rechaza como `migration.invalidReference` y un ciclo se rechaza como `migration.authoringInvalid`, antes de producir un manifest publicable;
4. dos pasos manuales que escriben el mismo objeto/campo sin orden explícito se rechazan; un `dependsOn` explícito permite el orden cuando esa secuencia está declarada;
5. pasos manuales independientes usan desempate lexicográfico por ID, de modo que invertir el orden de declaración produce exactamente el mismo `migration.steps`/grafo;
6. la frontera de biblioteca `runAddSqlSession` incorpora SQL manuscrito atómicamente al draft, calcula SHA-256 sobre bytes exactos, construye la `run` ref, recalcula `revisionHash` con la misma autoridad que el resto de autoría y rechaza duplicados sin reescritura parcial.

La persistencia del `CompiledAuthoringInfo` como `authoring: FileInfo`, sus hashes transitivos, la carga obligatoria desde `buildMigrationPlan` y el consumo por gates pertenecen al siguiente nivel de integración T22 y quedan expresamente fuera de este rojo.

### Rojo observado contra los slices #1+#2+#3 verdes

Los fallos son exactamente las fronteras aún diferidas:

- los casos de checks/`dependsOn` reciben `migration.authoringPending`;
- dependencia desconocida recibe el pending genérico en vez de `migration.invalidReference`;
- dos escritores sin orden todavía pasan, por lo que falta detectar el conflicto;
- pasos independientes conservan el orden de entrada en vez del desempate lexicográfico;
- `runAddSqlSession` todavía no está exportado.

## Límite de autorización del cuarto rojo

No se modifica producción con este patch. Si el desarrollador responde explícitamente `T21 fourth red approved`, queda autorizado únicamente:
