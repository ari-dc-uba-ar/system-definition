## Casos de aceptación

`test/migration-plan-contract-test.ts` fija las formas públicas serializables y las firmas puras de compleción/resolución.

`test/migration-plan-test.ts` cubre:

- catálogo A,B,C contiguo y resolución A→C como transiciones A→B,B→C en orden;
- A→A como path vacío que conserva refs `from`/`to` exactas;
- transición data-only con step SQL y metadata-only sin steps, sin inferir versión por cambios de schema;
- baseline de una sola release válido y catálogo de cero releases inválido;
- gaps, forks, release IDs duplicados, migration IDs duplicados y self edge;
- sistema discordante y hashes release/migration fuera de SHA-256 hex minúscula de 64 caracteres;
- origen/destino desconocido con `migration.invalidReference` y downgrade con `migration.downgradeUnsupported`;
- copia desligada de inputs al completar catálogo y ausencia de `planHash`/hashing en el path puro.

## Implementación

`src/common/migration-plan.ts` entrega los cuatro tipos Info requeridos y dos funciones puras:

- `completeMigrationCatalog` hace copia JSON estricta, valida al menos una release, mismo `systemId`, IDs únicos, hashes SHA-256 hex minúscula de 64 caracteres, cantidad exacta de aristas, endpoints consecutivos exactos y migraciones sin self edge; devuelve una copia desligada.
- `resolveMigrationPath` localiza origen/destino por `releaseId`, rechaza refs desconocidas y downgrade, conserva refs exactas en plan vacío y devuelve el slice lineal ordenado sin `planHash` ni I/O.

La validación de `MigrationInfo` dentro del catálogo comprueba forma serializable, IDs de steps, kind por posición (`check`/`sql`) y hashes de recursos. No intenta demostrar inmutabilidad histórica de artifacts: ese control pertenece al consumidor/artifact store de T06.
