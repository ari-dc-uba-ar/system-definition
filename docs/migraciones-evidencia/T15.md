# Evidencia T15 — Binding y vigencia de evidencia

## Alcance

T15 implementará la identidad exacta de evidencia de deployment descrita en `implementacion-migraciones.md` §14.2 y `migraciones-contratos.md` §9. El gate de entrada a apply debe consumir la última verificación durable del `deploymentId`, recomputar cobertura requerida y rechazar evidencia ausente, incompleta, fallida, alterada u obtenida para otro binding.

La identidad distingue explícitamente `operation:'install'` con `from:null` de `operation:'upgrade'` con release origen real. La cobertura mínima siempre incluye `artifacts`, `environment`, `structure` y `data`; `rehearsal` se agrega para upgrade productivo. El campo `status` durable no sustituye esa comprobación.

## Reutilización

- **R:** `Problem`, `ValidationResult`, `ReleaseRefInfo` del paquete raíz.
- **R:** `PgSession`, `JournalConfig` y el journal versionado de T10.
- **R:** hashes/refs de artifacts T06 y resultados semánticos de T13/T14 sólo como datos de evidencia; no se crea un segundo runner.
- **N:** módulo consumidor `src/evidence.ts` con tipos de binding/run, cobertura pura, persistencia ordinal y `checkApplyEligibility`.

## Rojo

Se agregan:

- `consumers/postgres-migrations/test/evidence-contract-test.ts`
- `consumers/postgres-migrations/test/evidence-test.ts`

Criterios fijados por el rojo:

1. evidencia ausente bloquea con `deployment.verificationMissing`;
2. `status:'passed'` leído del journal no habilita si falta cobertura requerida;
3. binding diferente en candidato, instalación, plan o configuración bloquea con `deployment.evidenceMismatch`;
4. el último run se decide por `ordinal`, no por timestamp, y un run incomplete/failed posterior invalida un passed anterior;
5. `recordVerification` deriva status desde checks y devuelve ordinal durable asignado por el store;
6. install usa `from:null` y no exige rehearsal; upgrade productivo sí la exige.

El contrato local esperado compila con un stub temporal de `src/evidence.ts` (`tsc --noEmit`, exit 0). Al retirar sólo ese stub, `tsc --noEmit` termina con exit 2 y exactamente dos diagnósticos `TS2307`, ambos por el import faltante `../src/evidence` (uno por cada test nuevo).

## Implementación

Se agregó `consumers/postgres-migrations/src/evidence.ts` y su export público. El módulo:

- modela el binding inmutable de install/upgrade y valida hashes, engine, scope e identidad;
- deriva `passed | failed | incomplete` desde la cobertura requerida, sin confiar en el `status` durable para autorizar;
- persiste runs en el journal con ordinal por `deploymentId` asignado dentro de una sentencia transaccional protegida por advisory xact lock;
- lee el último run por `ordinal DESC LIMIT 1`, nunca por timestamp;
- exige binding exacto antes de habilitar apply y devuelve los message keys de bloqueo del contrato.

`bootstrapJournal` ahora crea `verification_run` con unicidad `(deployment_id, ordinal)`. No se agregó una conexión oculta ni un receipt externo: todas las operaciones reciben una `PgSession` explícita.

Validación local aislada posterior a la implementación:

```text
tsc --noEmit (contrato T15 + módulos dependientes) -> exit 0
runtime evidence-test.ts -> 5/5 passing
```

Los cinco casos cubren missing/incomplete/tampered evidence, binding exacto, precedencia por ordinal durable, ordinal/status asignados por persistencia y la diferencia install/upgrade. Esta validación local no sustituye la suite autoritativa en Docker Node 24.

## Verificación autoritativa

El desarrollador ejecutó en Docker Node 24:

```text
docker compose exec node npm test
core -> 146 passing (379ms)
consumer -> 51 passing (364ms)
```

Dentro del consumidor, los cinco casos `deployment-bound verification evidence` pasaron:

1. evidencia faltante bloquea y la cobertura requerida se recomputa sin confiar en un `status` declarado;
2. binding exacto de candidate, installation, plan y configuration;
3. orden por ordinal durable: una corrida más nueva incompleta/fallida invalida una pasada anterior;
4. el store asigna durablemente el ordinal y deriva el status de la cobertura al registrar;
5. `install` con `from:null` se distingue de `upgrade`, y rehearsal sólo es obligatorio para upgrade productivo.
