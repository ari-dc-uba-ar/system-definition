# Evidencia T14 — Ensayo sobre copia identificada

## Estado del rojo

T13 quedó cerrado por aprobación explícita del desarrollador el 2026-09-28. T14 parte del contrato de [implementación §13.3](../implementacion-migraciones.md#133-ensayo-con-copiabackup) y [contratos §9](../migraciones-contratos.md#9-evidencia-y-gate-de-deployment): una actualización productiva requiere ensayo del segmento real sobre una copia identificada; un install nuevo no fabrica un backup de origen; y el ensayo nunca sustituye checks reales sobre el target bajo mantenimiento.

## Superficie fijada por los tests

Los tests nuevos fijan un módulo `rehearsal.ts` con:

- referencia de copia identificada por `copyId`, procedencia, installationId, release/hash origen y schemas;
- provider que abre únicamente la copia preparada por infraestructura y conserva ownership del handle; el motor no implementa restore ni deriva cleanup desde un DSN;
- `rehearseUpgrade`, que ejecuta el `MigrationPathInfo` completo mediante el motor transaccional existente y produce un reporte con origen, alcance, migraciones, artifacts y checks ejecutados;
- `targetChecksRequired: true` en el reporte: el ensayo no autoriza a omitir pre/postcondiciones reales bajo mantenimiento;
- `checkRehearsalRequirement`, que exige ensayo válido para `production + upgrade`, rechaza ausencia/fallo/mismatch y no exige backup para `install` con `from:null`.

Los casos runtime exigen además:

1. A→B→C ejecuta ambas transiciones sobre la misma copia y reporta hashes/IDs exactos;
2. si el head durable de la copia no coincide con el origen declarado, no se ejecuta ningún step;
3. ausencia, fallo o copia de otro artifact bloquean un upgrade productivo;
4. install nuevo de producción no requiere backup inexistente;
5. un handle no reconocido por el provider no ejecuta SQL ni se limpia.

## Implementación

Se añadió `consumers/postgres-migrations/src/rehearsal.ts` y su export público. La implementación:

- valida que copia declarada, path y scope describan el mismo origen;
- abre la copia mediante el provider y exige `owns(handle)` antes de emitir cualquier SQL;
- relee el head durable del journal sobre la copia y exige `installationId` y release/hash origen exactos antes del primer step;
- ejecuta el segmento completo con `executeMigrationPath` y el mismo motor transaccional de T11;
- captura releases, migraciones, recursos y checks realmente cubiertos, incluyendo invariantes target resueltos por transición;
- produce `targetChecksRequired: true`, dejando explícito que el ensayo no sustituye los checks reales bajo mantenimiento;
- destruye sólo handles cuya propiedad fue demostrada por el provider y agrega fallos de cleanup al resultado sin convertir un fallo previo en éxito;
- implementa `checkRehearsalRequirement`: `production + upgrade` exige ensayo pasado y exacto; ausencia, fallo o mismatch bloquean; `install` con `from:null` no inventa backup.
