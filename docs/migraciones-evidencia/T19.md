## Segundo rojo propuesto — exactitud y compatibilidad estática

Archivo nuevo: `consumers/postgres-migrations/test/migration-authoring-static-test.ts`.

Este rojo fija la parte de §5 que el primer slice dejó explícitamente pendiente:

1. `defineDataMigration` preserva literales de `id`, transformación e `identity`;
2. source refs se restringen al snapshot literal `from` y rechazan campos inexistentes o refs del lado `to`;
3. `transformation` se restringe a `keyof context.transformations`;
4. `arguments` debe tener exactamente las keys de `TransformationInfo.parameters`;
5. outputs usados por `writes` deben existir en la transformación seleccionada;
6. targets se restringen al snapshot literal `to`;
7. un output nullable no satisface un target NOT NULL;
8. los errores se localizan en la llamada tipada y no se reemplazan por un contrato runtime ancho.

El primer slice dejó `CompatibleDataMigration<C,D> = D` deliberadamente permisivo y las refs anidadas todavía usan nombres `string`. Por eso el rojo esperado no es un módulo ausente: TypeScript debe informar `TS2578: Unused '@ts-expect-error' directive` en los casos que hoy compilan indebidamente. Un focused compile local del test produjo **9 TS2578**: source field, source side, arguments, output name, target field, domain mismatch, exactitud recursiva de write, exactitud recursiva de port y nullability output→target. El typo de `transformation` ya está cubierto por `keyof C.transformations` y su `@ts-expect-error` sí se consume desde el inicio.

No se modifica producción con este patch. `source-selection.ts` se aborda después de fijar este surface estático, porque el wizard depende de poder ofrecer sólo refs/domains válidos. `authoring-cli.ts` permanece para un red posterior.

## Tercer rojo propuesto — selección de fuentes y joins explícitos

Archivo nuevo: `consumers/postgres-migrations/test/source-selection-test.ts`.

Este rojo fija la frontera `source-selection.ts` sin tocar CLI:

1. una selección de tabla única deriva domains/field refs desde el snapshot histórico `from`; el autor no vuelve a declarar tipos que puedan divergir del SSOT;
2. el query generado es determinístico para la misma selección y cita schema/tabla/alias/campo por componente;
3. los joins requieren pares de igualdad explícitos: no se adivinan por nombres coincidentes;
4. un `LEFT JOIN` con filas sin correspondencia incluidas amplía a nullable los ports del lado derecho sin borrar su `FieldRefInfo` histórico;
5. una selección que excluye deliberadamente filas (`INNER`/`whenUnmatched=exclude`) exige `coverageChecks` explícitos; no se registra pérdida de cobertura silenciosa;
6. `identity` debe referenciar ports existentes y no-null después de aplicar la semántica de join; una identidad nullable o inexistente bloquea;
7. la API esperada es `buildSourceSelection(context, def): ValidationResult<GeneratedSourceSelectionInfo>`, donde el resultado contiene `selection: SourceSelectionInfo` y los bytes SQL (`sql`) cuya referencia `query` queda ligada por hash.

Este slice no incorpora filtros SQL complejos, agregaciones, escritura destino ni interacción. Esos casos usan query explícita/contrato y las capas posteriores ya especificadas; el wizard no inventa semántica. `authoring-cli.ts` sigue fuera de alcance.
